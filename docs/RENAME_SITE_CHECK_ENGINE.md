# Check Engine site rename

## Build modes

`scripts/brand.py` owns the name, short name, host, base URL, command name, tagline and former name.
An unset `SITE_BRAND` selects `docket`. Set it to `checkengine` for Check Engine SEO on checkengineseo.com.
An unknown value stops the build. The default in that module is the cutover line.

The page assembler brands visible words, text attributes and JSON-LD values after joining the page.
It keeps URL paths, query strings, file names, code names, class names, IDs and event tags.
The footer, About page and home page get the former name from `FORMERLY`.
The download and developer pages each explain the `docket` command alias once.
The home title uses the requested plain-form tagline.

The build also writes a sorted array of paths to `site/_redirect-map.json`.
It contains file paths and the slash paths served by each `index.html`, including old redirect pages.
This derived inventory is outside the build-id hash. Its regression check compares it with the actual file tree.
That keeps the existing default build ID stable when the inventory is added.

`data/redirect-pages.json` holds the source of the existing redirect pages.
This lets either mode rebuild those pages after the other mode.
Page hashes are also stored by mode. Check Engine uses `data/page-lastmod-checkengine.json`.
The churn gate compares it with the deployed Docket hashes until a Check Engine baseline exists.
The gate still needs `DOCKET_SITEWIDE_REASON="Rename to Check Engine"` for the rename.

The existing checker Worker reads `src/site-brand.js`, generated by the Python build from the same module.
Its CORS origin, guide links, site links, icon URLs and display name follow the selected mode.
Its MCP protocol name stays `docket-seo`.
The Worker tests use fake fetch functions.


## Google verification file

The CEO has not supplied the Google file yet. This change adds no verification
file. The steps below are for a later job with permission to add the real file.

### How static files reach the host

The build writes pages directly into `site/` and keeps other files already in
that tree. There is no general static-source directory copied into the root.
`write_static()` in `scripts/build.py` copies only named files from `data/` to
`site/data/`, and writes `CNAME` and `.nojekyll`. A file placed only in `data/`
does not become a root URL. The explicit copy list prevents private datasets
from being published by a broad file pattern.

`scripts/deploy.sh` publishes the `site/` subtree as the root of `gh-pages`.
GitHub Pages serves that branch. `.nojekyll` bypasses Jekyll processing.
The Python build adds no redirect for a root HTML file or a file under
`.well-known/`. Its `_redirect-map.json` inventory includes every built file,
so a new file is also available to the rename redirect inventory.

The repo does not set response headers for individual GitHub Pages files.
The build alone cannot prove the live status, redirect chain or MIME type.
An HTML extension should be served as HTML and a JSON extension as JSON, but
both must be checked on the target host after release. The old-domain rename
redirect is separate from serving a file on the new canonical domain.

### Steps when the file arrives

1. Keep the exact filename and bytes Google supplies. Confirm which hostname
   Google asks to verify. A token file must keep its exact contents in both
   brand modes. Do not pass it through `render()` or the brand text pass.
2. Store the approved input in a dedicated path such as
   `data/static-verification/google<token>.html`. For a JSON file, use its
   supplied name under `data/static-verification/.well-known/`.
3. Add an explicit copy in `write_static()`, using `shutil.copy2()` from that
   exact input to `SITE / "google<token>.html"`, or to the exact supplied path
   below `SITE / ".well-known"`. Create the destination parent directory for
   a nested path. Require the input to exist. Keep the copy outside the
   `site/data/` dataset list. Avoid a wildcard copy or a new sitemap entry.
4. Build both brands with the normal offline build commands above. Compare
   the source bytes with the built bytes. Confirm the exact slash-prefixed
   file path appears in `site/_redirect-map.json`. Extend the regression
   test's expected file inventory for the approved addition.
5. Have Claude review and release the new static input and copy step through
   the usual process. After that release, request the exact HTTPS file URL
   on the hostname being verified, with redirect following turned off.
   Require status 200, no Location header, and bytes matching Google's file.
   For `.html`, check `Content-Type: text/html` with any charset suffix.
   For `.json`, check `Content-Type: application/json` with any charset suffix.
6. If the request redirects, check the hostname, HTTPS setting and Pages
   custom-domain setting. If the MIME type is wrong, resolve it with the host
   before completing verification. A canonical tag or HTML refresh is not a
   substitute for the supplied static file. Submit verification in Google's
   Connected Apps only after the exact URL passes those checks.
